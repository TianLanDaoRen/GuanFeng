# 观风 · GuanFeng

> 手表上的离线微气象仪表 —— 为 OPPO Watch 4 Pro（OWW221）而做

观风把手腕上的气压计、心率与腕温，变成一台**不依赖网络的短临气象仪表**：
在手机摔坏、手表也没网的处境下，抬腕就能知道未来 6–12 小时会不会变天，
以及此刻外界环境与自身状态是怎么对应的。

整个项目的赌注只有一句话：**这台机器有气压计，而气压计不需要网络，就能算出天气走向。**

---

## 一、为什么做这个

1. **离线是唯一稳的路径。** 手表的蓝牙共享网络只有 80–120 KB（官方口径），
   强网络型应用在这条管子上会失效。而气压短临预报把"预报"这件事从云端搬到了本地。
2. **系统自带天气恰好是要被替代的那个。** 设备上已装 `com.heytap.wearable.weather`，
   但它依赖手机与网络——正好是"手机坏了"时最先失效的一环。
3. **架构上主动避开三条死线。**
   - 官方明确"不支持应用在后台运行" → 不做常驻任务，改用前台短采样 + 每行即时落盘；
   - indicator 只支持导航 / 运动 / 媒体播放三类 category，**天气类没有合法 category**
     → 硬接接不上，索性从架构上不设计常驻任务；
   - 网络权限属敏感权限、用户同意前不得联网 → 本应用**一个网络权限都不申请**。

## 四、算法：把「天气」和「高度」拆开

### 4.1 核心命题

气压计读到的是**「天气 + 高度」的叠加信号**。而爬一层楼就有约 0.36 hPa——
**这已经和一整天天气变化的量级相当**。绝大多数气压天气小工具的死穴，
就是把爬楼误读成天气剧变。

### 4.2 物理底数（决定了阈值怎么取）

| 变化来源 | 速率 |
|---|---|
| 最慢爬坡（0.05 m/s） | 0.36 hPa/min |
| 正常爬楼（0.25 m/s） | 1.80 hPa/min |
| 电梯（0.50 m/s） | 3.60 hPa/min |
| 缓慢天气变化（3 hPa/3h） | 0.017 hPa/min |
| 极端天气上限（10 hPa/3h） | 0.056 hPa/min |

换算基准：海平面附近约 **−0.12 hPa/m**。

两者相差 1–2 个数量级，因此判定阈值取 **0.1 hPa/min**：
比极端天气上限高 1.8 倍、比最慢爬楼低 7.2 倍。余量偏窄的那一侧，
由"**必须同时存在垂直运动证据**"这条与条件兜住——台风逼来时人通常不在爬楼。

### 4.3 三道闸门（每一道都是被真机数据逼出来的）

**闸门一 · 30 秒速率基线。**
真机静置实测：相邻 2 秒的气压抖动可达 0.02 hPa，折算 **0.6 hPa/min**，
是判定阈值的 6 倍——噪声自己就能伪造出"高度事件"。而同一份数据在 30 秒尺度上
最大变化是 **0.0000 hPa**。所以速率一律基于 ≥30 秒的基线计算。

**闸门二 · 垂直位移状态机。**
真实电梯的匀速段加速度接近 0、也没有步数，但气压仍以数 hPa/min 持续变化。
只认瞬时证据会把它误判成天气剧变。因此改为：由一次瞬时垂直证据**点火**，
此后只要速率仍超阈值就持续计入高度事件，直到速率回落才退出。

**闸门三 · 绝对量门限。**
静置 2–6 分钟的窗口内气压总跨度只有 0.04–0.05 hPa，却能被回归算出
`−0.556 hPa/h` 且 **R² = 0.52**——速率判据与拟合优度都拦不住它，因为那确实是一条
很干净的微小直线。因此再加绝对量门限：窗口内实测变压低于 **0.5 hPa** 时，
一律按"平稳"处理，不谈方向。

### 4.4 高度换算

累计高度偏移 ÷ 0.12 hPa/m 即得米数，符号取反（降压即上升）。
副产品：`elevationMeters` 同时就是**今日累计爬升**。

### 4.5 已知取舍（诚实记录）

爬楼期间若天气同时在变，那一小段天气变化会被一并计入高度偏移。
量级可接受——爬楼持续数分钟，天气变化约 0.02 hPa/min，5 分钟也只误吸 0.1 hPa。

### 4.6 风雨规则目前**未校准**

`WeatherRule` 是"气压趋势 ↔ 降水"定性关系的**启发式映射**，
没有用任何真实降水观测数据校准过，因此返回结果里 `calibrated` 恒为 `false`。
将来若要用真实数据校准，只需替换这一个文件，内核不必改动。

## 五、置信度闸门
只有 `TrendConfidence.OK` 时才允许对外给风雨结论；否则一律"未知"：

| 值 | 触发条件 |
|---|---|
| `SHORT_WINDOW` | 窗口覆盖率 < 30% |
| `NOISY` | 有方向性变化时，拟合优度 R² < 0.4 |
| `INSUFFICIENT` | 样本数不足 |
| `OK` | 以上皆非 |

**为什么闸门设在引擎层而不是 UI 层**：实测日志里出现过「窗口 0.14 分钟、R² 0.029，
却报出缓升 1.382 hPa/h」以及「窗口总跨度 0.02 hPa、却报缓降 −0.556 hPa/h 且标为可信」
——让 UI 去判读已经太晚，错在源头就得在源头拦。

> ⚠️ **窗口长度决定读数可信度**：短窗口里噪声很容易凑出像样的斜率
> （实测 2 秒尺度的噪声折算 0.6 hPa/min，是判定阈值的 6 倍）。
> 现采用**正式 3 小时窗口 + 5 秒聚合**，同样的噪声只能折算约 0.023 hPa/h，仍比 0.5 hPa/h 的
> 判定边界低一个数量级（**这个数是推算**：0.013 是 15 秒聚合时代的实测值，聚合窗口缩到 1/3、
> 平均的原始读数少 3 倍，白噪声按 √3 放大，尚未重新实测）。
> 代价是覆盖率闸门要求窗口至少铺满 30%（约 54 分钟）才给结论——
> **刚启动时显示「样本未铺满」是正确行为，不是故障。**
> 历史会话会在启动时被续接（见第六节），所以服务重启不会让窗口从零开始。

## 六、数据落盘与离线复盘

### 两个时间尺度

| 尺度 | 节奏 | 用途 |
|---|---|---|
| 实时 | 2 秒（`LIVE_TICK_MS`） | 界面上的「此刻」读数（气压 / 心率 / 腕温 / 光照）。不喂引擎、不写盘 |
| 样本 | **5 秒**（`SAMPLE_INTERVAL_MS`） | 聚合后喂引擎并落盘。3 小时窗口 = **2160 个样本**，落盘约 **1.7 万行/天**（≈2 MB） |

> 这张表原写作「15 秒 / 720 个样本 / 5760 行」，是 15 秒采样年代的旧值，
> 2026-09-11 核对代码时改正。**满勤 720 是"每小时"，不是"3 小时"**——
> 12 个/分钟 × 60 分钟 = 720，这一点在排查小时归档缺口时是判据。

聚合口径三路各不相同：气压取**中位数**（抗单点尖峰）、垂直加速度取**峰值**
（取平均会让抬腕与电梯脉冲消失）、步数**求和**。

### 跨会话续接

启动时从最近的 CSV 反向读取窗口内的样本，让 3 小时窗口在服务重启后接着算——
否则每次重启都要再熬一小时才有可信读数。

**两条铁规则**：① 只回填窗口内的样本；② **遇到断档就停**。进程没运行的那段时间
没有数据，把空洞两端的样本接起来做回归会算出一段根本不存在的趋势。
**宁可窗口短一点，也不要跨空洞拟合。**

**续接之外还要补两条**。第一条（2026-09-11）：小时归档的累加器也活在内存里，
重启会让**当前这一小时已累积的部分**从 `hourly.csv` 里消失。实测 22:14 重启后，
22:00 那行只有 **545/720** 个样本。现在启动时会用刚回填的样本把本小时补齐
（`backfillCarriedOver`，纯函数、有单测），并在日志里留一行
`小时归档补齐：启动前本小时已有 N 个样本` 供事后核对。

第二条（2026-09-12）：上面那条只覆盖**当前小时**。若应用在某个整点中途被停掉、
而重启时已经跨了好几个小时，那个整点就会**整行消失**——真机实证：
睡眠模式 02:59 停掉应用，02:00 那一小时没到点，于是它从归档里没了，
可样本文件里那 59 分钟完整存在。因此启动时另有一道**归档修补**：
从样本文件尾部折叠出最近 24 小时的小时桶，只补"归档里整点缺失"的**过去**小时
（`missingHourBuckets`，纯函数、有单测；append-only，绝不改动已有行）。
日志里对应 `小时归档修补：补回 N 个缺失的整点`。

**补写的行只有气压、没有体感**（原始 CSV 里本就没有那一刻的心率/腕温）。
已有但不满勤的行**保持原样**——拿无体感的行去替换是降级，不是修复；
所以 09-11 22:00 那行 `545/720` 的疤痕会一直留着，如实记录当时被重启切掉了一段。

### 落盘

**单一文件**：`guanfeng_samples.csv`（每次启动不再新建文件，见 9.2）。
超过 30 MB 时丢掉最旧的行、保留最近 25 MB——因此原始明细只能回溯约两周，
**长期趋势必须读 `hourly.csv`**。

```
/sdcard/Android/data/com.yisiyun.guanfeng/files/guanfeng_samples.csv
```

- 用 `getExternalFilesDir(null)` → **可直接 `adb pull`，不需要 `run-as`**，不受分区存储限制
- **每行即时追加**，不是退出时才写 → 进程被杀也只出现"断档"而不丢数据
- 断档可由时间戳列直接识别（相邻样本间隔 > 3× 采样周期）

列（以真机拉到的文件为准，2026-09-11 核对）：

```
timestamp_ms, clock, pressure_hpa, vertical_accel, steps, rate_hpa_per_hour,
delta_hpa_3h, grade, weather_samples, elevation_events, elevation_meters,
r_squared, window_minutes, coverage_pct, confidence,
resting_heart_rate_bpm, light_delta_10min, weather_pressure_hpa, light_lux,
vertical_displacement_m
```

**注意 `steps` 列**：它曾长期全为 0——因为 `ACTIVITY_RECOGNITION` 只在清单里声明、
从没在运行时申请，计步传感器注册被 SensorService 直接拒绝（见 9.11 末尾）。
已于 2026-09-11 修复，但修复之前的数据这一列不可用。

### 离线复盘

```bash
adb pull /sdcard/Android/data/com.yisiyun.guanfeng/files/ ./guanfeng-logs/
python3 tools/analyze_guanfeng_log.py guanfeng-logs/
```

工具会回答四件事：
1. 记录时长与**断档**位置（进程被压制/回收的证据）
2. 抓到几段**垂直运动**、各自位移多少米、步数多少
3. **解耦有没有生效**——把"引擎输出的天气速率"与"对原始气压直接回归的朴素速率"
   逐点对照：朴素速率在高度事件期间会飙高，引擎速率应当纹丝不动
4. **置信闸门拦下了多少**（可信 / 窗口太短 / 趋势不稳）

## 九、气压 × 体感 页与 AI 报告

### 9.1 气压 × 体感（第四屏，原「关联」）

把体感打卡点按**当时的气压高度**叠在小时均值曲线上，一眼看出打卡是否扎堆在气压骤变时。

两个必须踩对的点：

1. **长视图不能直读原始样本。** 原始采样 5 秒一个点，一周约 12 万行 / 15 MB；
   在手表上直接读会又慢又占内存。因此按小时折叠成桶，
   而且**边读边折叠**，不把整周样本留在内存里。
2. **喂进桶的必须是天气分量，不是气压计原始读数。** 这是本项目最值得记的一次教训：
   解耦只在趋势窗口内做，长视图却用了原始读数，于是一趟电梯（约 9 hPa）
   会被算成一次「气压大变化日」，打卡点也会落在被高度污染的位置上。修法见 9.7。

### 9.2 单一采样文件 + 体积上限（碎片化问题的正解）

原先"每次启动一个新文件"，实测 11 小时产生 **14 个**（重启就新开），碎片化且难以回看。

现在改为**唯一文件 + 只追加**（主人的设计）：

| 文件 | 内容 | 上限 |
|---|---|---|
| `guanfeng_samples.csv` | 5 秒采样明细，跨会话连续 | **30 MB**；超限时紧凑化，丢最旧、保留最新 25 MB |
| `hourly.csv` | 小时汇总（气压分量 + 心率/腕温/光照），约 1 KB/天 | **永不删除** |
| `checkins.csv` / `weather_observed.csv` | 体感打卡 / 天气实况 | 永不删除（手工产生的数据无法重建） |
| `power.csv` | 耗电自记录（电量 % + 本进程 CPU 时间） | 永不删除 |

关于"append 前 pop 最远记录"：如果每追加一行都去删最旧的一行，每次都会退化成
**O(文件大小) 的重写**——30 MB 文件一天会被重写上万次，手表扛不住。
所以实现为**超限时紧凑一次**：效果相同（有上限、丢最旧），
代价从每天上万次重写降为几周一次。

恢复 3 小时窗口时只读文件**尾部 2 MB**（5 秒采样下约 1.7 万行 ≈ 24 小时），
不再从头扫过整周数据。

**不要"把旧数据提取后抄进新文件"**——那会让同一批样本在分析时被算两遍，
而且很难事后发现。单一文件 + 跨行读取才是正确做法。
实测（本机 pull 的 14 个旧文件、1865 行）：跨文件与文件内均**零重复时间戳**。

### 9.3 主动提醒：两条系统通道都被堵死之后的最终设计

#### 平台事实（真机实测，非推测）

手表有两条通知通道，**第三方应用能用的只剩一条**：

| 通道 | 实测结论 |
|---|---|
| 普通通知 | SystemUI 有 `canPost` 白名单，**只放行"手机同步过来的"通知**。我们本地发的通知能进系统数据库（`dumpsys notification` 里看得见 `id=2001 importance=4`），却连提醒流程都不走——点下去毫无震动。对照实验（换一个包发通知）拿到明示拒绝：`[canPost] it is not allowed, return false!` |
| indicator | `enqueueIndicatorNotification`，不受白名单限制，**一定会出现在表盘顶部**；但真机确认它**只显示图标、不显示任何文字** |

设置里的「运营消息推送」（`.notification.push.OperateMessagePushActivity`）只关 OPPO 自家应用的营销推送，与本项目无关。完整证据链见 oppo-watch skill 的 `oww221-probe-findings.md`。

#### 最终设计

| 环节 | 做什么 | 为什么这么做 |
|---|---|---|
| 1. 唤起注意 | **自己调 `Vibrator`**（三短一长） | 通知的提醒流程被拦，只能直驱马达。系统侧可见 `aidl_vibrator: Vibrator on for timeoutMs: 600` |
| 2. 讲清内容 | 落一条**待确认提醒**（SharedPreferences，跨进程死亡存活） | 唯一能把"是什么事"讲清楚的通道，是应用自己的界面 |
| 3. 交付 | 用户**下次回到应用时**弹出确认卡片，点「我已知晓」才消失 | 提醒的价值在于被看到；自动消失等于没提醒 |
| 4. 留痕 | 仍发一份通知 + 更新 indicator 文案 | 二者都不上屏/不显字，但让系统记录里留下当时状态，便于事后核对 |

冷却 2 小时、回落后重新武装——**被关掉的提醒等于不存在**，所以宁可漏报也不刷屏。

#### 天气实况（校准的真值来源）

记录页提供 下雨 / 起风 / 晴 / 阴 四个按钮，落盘时**把当时的判断一并写入**
（倾向、速率、变压、置信度）。这样之后可以直接算：报「高」时实际下雨的比例（命中率）、
下雨前我们报的是几（漏报率）。只记"下雨了"的话，事后还得去别的时间线里对齐，既麻烦又容易对错。

刮风值得记录，但**不是因为它能提高预测**：手表没有风速传感器，
而且风与气压梯度本来就是同一个天气系统的两面（信息冗余）。它的价值是**真值**。

### 9.4 耗电归因

第三方应用**读不到自己的 mAh**（BatteryStats 属系统权限）。所以分两步：

- 应用内 `power.csv`：每 5 分钟记 电量 % / 是否充电 / 电池温度 / **本进程累计 CPU 时间**
  / 已运行时长。前后相减就是这段时间我们真正吃掉的 CPU。
- 权威数字用这条命令：

```bash
adb shell dumpsys batterystats --charged com.yisiyun.guanfeng
```

判读方法：**如果我们 CPU 时间很低、电量却在掉，那掉的电就不是我们吃的。**

#### 2026-09-11 实测结论（两条口径打架，以机理为准）

| 口径 | 读数 | 可信度 |
|---|---|---|
| AOSP 功耗模型 `dumpsys batterystats` | 应用累计 **20.8 mAh**（cpu 11.4 + sensor 9.42，wakelock ≈ 0） | **低**。连续观测 15 分钟三位数字一个都没动，说明这台表的 `power_profile` 对我们用的传感器给不出分辨率 |
| OPPO 自带「电池管家」 | 当天耗电的 **31.45%**，累计活动 7h36m、前台 39min | 中。按活动时长加权估算，口径与 AOSP 不同 |
| 应用自记 `power.csv` | 进程 CPU **5.7% 单核**（22:55→23:10 窗口 +53.8s/15.6min） | 高，但只覆盖 CPU |
| 整机电量斜率 | 应用运行时段 **≈4%/h**，装机前 ≈1%/h | 高 |

**决定性的不是上面任何一行，而是机理**：`dumpsys sensorservice` 显示
`HEART_RATE active-count = 1` —— 全表只有本应用一个客户端，
即"我们让手表的 PPG 光电传感器 7×24 亮着"。
PPG 是手表上最贵的单一传感器（LED 驱动电流），主人说"耗电跟睡眠监测差不多"
正是同一个原因。因此判定：**AOSP 的 20.8 mAh 严重低估，OPPO 的 31.45% 更接近真相。**

对应的动作（见 9.11）：心率/腕温由常开改为脉冲采样。

**另一条事实（此前我误判过，已更正）**：`power.csv` 的 `app_elapsed_min` 在
22:14:35 与 23:14:31 两次归零，我一开始把它写成"系统定期回收前台服务"，
**这是无证据的推断，已撤回**——23:14 那次已由主人确认是自己安装新构建，
22:14 那次至今**未归因**（安装、手动重启、被回收都有可能，不编故事）。

真正站得住的依据只有两条：可用内存实测很低（`procstats` 里 `Free` 最低 24 MB），
以及**每次安装新构建都必然重启进程**——后者在开发期是每次都会发生的。
天气过程锁存落盘（见 9.6）由这两条支撑，不需要"系统每小时杀一次"这种未证实的假设。

### 9.5 AI 报告（可选功能）

核心功能全部离线；这一项**只在用户显式点按钮并在弹窗确认后**才发起，
代价（需要联网、要上传聚合统计）由用户自己判断。

- **发什么**：气压与打卡的聚合统计（天数、有效天、气压大变化日与日期、打卡次数与标签/强度分布、
  每日气压极值），以及 **心率 / 腕温 / 光照的小时级统计与明细**（`body_context`）。
  **不发**逐条打卡记录、备注原文、体征逐点读数、任何设备或用户标识——
  `AiDigestTest` 里有一条测试专门断言逐条记录与备注不外泄。
- **为什么带体感**：头痛未必来自气压，也可能是发热（腕温升高）。
  只给气压，模型就只能在自己的数据里硬找关联；给了体感，它才能排除混淆因素。
- **体感一律给中位数与极值，不给瞬时值**：袖子翻一下、进一趟空调房，腕温瞬时能跳好几度。
  归档本身就是按小时取中位数（实测 33.0/36.2/33.2 三个读数：均值 34.13、中位数 33.2，
  被污染的均值会一路传进报告）。
- **两段口径**：`all_history` 与 `recent_7_days`，让模型分别观察全局与近期。
- **硬约束写在 `systemInstruction` 里**：只说「可能有关联」、必须点明样本量小、
  禁止任何医学诊断、不要输出表格与代码块（腕上放不下）。
- **返回是模型原生 Markdown，且服务端会追加固定标语帧。**
  后者**不是模型输出的**，光靠提示词约束模型解决不了，必须由调用方切除：
  `MarkdownLite` 按「标语行 + 其上方紧邻的空行与分隔线」一起切除，
  不写死精确文本，装饰微调也能吃掉。
- 接口：`POST https://yunsisanren.top/gualing-core/ai/plain`（明文口，免 apikey）。
  命中限流后退避 15 秒自动重试一次，**并把该状态显示出来**——
  退避可以是自动的，但不能是无声的，否则手表上看起来像卡死。

### 9.6 天气过程状态机（下雨是有始有终的过程）

**这一节的模型是主人提出的，它取代了我原先"回看最近 6 小时降幅"的做法。**

滑动窗口只能回答"过去一段时间降了多少"，回答不了"现在是不是还在一场过程里"。
它的漏洞很直白：**降完之后一直下着雨超过 6 小时，窗口一滑照样忘干净**，
于是又开始报「平稳 · 无需带伞」——原来的补丁只挡住了 6 小时以内。

状态机的规则：

| 环节 | 规则 |
|---|---|
| 进入 | 天气分量自参照最高点累计降幅 ≤ **−1.5 hPa** → 「可能下雨」 |
| 维持 | **只要没满足解除条件就一直挂着，与过了多久无关** |
| 解除 | 自本轮最低点回升 ≥ **1.5 hPa**（低压已过） |
| 新一轮 | 解除后再次下降，参照点重置并重新进入 |

**为什么两个门限要同量级**：进入与解除若不对称（比如解除只要回升 1.0），
雨带间歇期气压本来就上下抖（±0.6，峰峰 1.2），照样越过解除门限 →
状态来回翻、提醒跟着刷屏。两个门限都代表"天气尺度上的真实变化"
（远高于传感器噪声 0.1~0.3、也高于雨带抖动 0.5~1.0），
中间那片灰色地带**保持原状态**——这就是迟滞。
有一条"120 分钟内零次翻转"的测试守着这个性质。

状态机也是气象仪器的通行做法：风暴警报一旦挂上就锁存，直到气压回升才摘掉。

**锁存必须落盘（2026-09-11 补）**。这条最初是漏的：状态机只活在内存里，
进程一被回收就清零，重启后第一帧样本把当时气压当成参照最高点，
于是"已经降了 3 hPa、雨正在下"被彻底忘掉，又回到「平稳」——
与"挂上就不摘"直接矛盾。手表可用内存确实很紧（`procstats` 实测 `Free` 最低 24 MB），
但**触发这次修复的直接证据是"每次装新构建都会重启进程"**，
这条在开发期必然发生，不需要假设系统会定期杀我们。

现在 `active / peak / min / start_ms / drop` 一并写进 `recorder_state.txt`
（与高度偏移同一份文件、同一个 5 分钟落盘节奏），启动时读回。
带一条过时判定：快照年龄超过 6 小时就丢弃——隔夜再打开应用，
昨天那场雨不该继续算数。

**这个门限是已裁决的取舍，不要再"优化"它**（主人 2026-09-11 定）：

> 直接保守吧，毕竟你无法预估空白期间会发生什么。比如天气已经转好，本就应该退出。

对手方案是用"断档前后的净变压"决定要不要续挂。它听起来更连续，但前提是
**"这段空白里气压是单调变的"**——而我们完全没有观测，无法排除中途转晴再转阴。
拿两个端点去推断中间没看过的过程，正是这个项目从第一天就在避免的事
（同一个道理见第六节的"遇到断档就停"）。**宁可每早重置，也不编中间的过程。**

**真机已确认生效**（2026-09-11 23:14 装新构建后重启，`recorder_state.txt`）：

```
resting_hr=67.0
elevation_offset_hpa=0.000
episode_active=0
episode_peak_hpa=1002.821
episode_min_hpa=1002.821
episode_start_ms=1789139671712
episode_written_ms=1789139671932
```

这次重启**没有丢任何已采集数据**：日志里是 `从历史续接 2128 个样本`。

### 9.11 传感器占空比：省电的唯一有效动作是"关掉"，不是"降速"

真机 `dumpsys sensorservice` 抓到的我们持有的传感器：

| 传感器 | 之前 | 现在 | 理由 |
|---|---|---|---|
| 气压 `Press_Sensor` | 5 Hz | **5 Hz 不变** | 5 秒聚合节奏靠它撑，一趟 45 秒电梯只有约 9 个样本 |
| 重力 / 线性加速度 | 5 Hz | **5 Hz 不变** | 竖直位移证据，改了会动到已用真实数据验证过的解耦链路 |
| 光照 `Light_Sensor` | 200 ms | **5000 ms**（HAL 钳到 1680 ms） | 10 分钟趋势只需要首尾两点。**但省不了什么电**：该传感器 `active-count = 2`，系统自动亮度自己也挂在上面（500 ms），器件本来就亮着 |
| 心率 `HEART_RATE` | **常开** | **每 10 分钟开 20 秒** | 见下 |
| 腕温 `0x110b7` | **常开 5 Hz** | **并入同一个 20 秒窗口** | 分钟级慢变量被 5 Hz 采，250 倍过采样 |

**为什么心率必须"关"而不是"降速"**：`HEART_RATE` 的 `maxRate = 1.00 Hz`，
我们请求 5 Hz 也被硬件钳到 1 Hz——**降速率产生不了任何差异**。
而它的 `active-count = 1`：全表只有本应用一个客户端，
即"我们让手表的 PPG 光电传感器 7×24 亮着"。PPG 是手表上最贵的单一传感器
（LED 驱动电流），主人说"耗电跟睡眠监测差不多"正是同一个原因。

**真机已确认生效**（23:14 那次的 logcat）：

```
SensorService: enable,handle=21,...   (23:14:26.760)
SensorService: enable,handle=69815,... (23:14:26.753)
GuanFengRecorder: 体感采样窗口开启
SensorService: disable,handle=21,...   (23:14:46.764)
SensorService: disable,handle=69815,...(23:14:46.767)
GuanFengRecorder: 体感采样窗口关闭      ← 恰好 20 秒
```

窗口关闭后 `dumpsys sensorservice` 的 active 列表里
`0x15 HEART_RATE` 与 `0x110b7` 双双消失（active-count 归 0），PPG 真正断电。

**代价（如实记录）**：心率与腕温不再连续，界面上的心率是"最近一次测到的值"，
最坏情况会陈旧到 10 分钟。对天气判定无影响（这两个量本来就不参与判定，
只进 AI 报告的 `body_context`），但对"此刻心率"的读数要按陈旧值理解。

### 9.7 天气分量与高度解耦（长视图）
引擎只做窗口内解耦，且它是**相对于窗口起点**的；调用方必须从每步回报里
把高度分量累加起来，才能得到与窗口无关的序列。因此：

- 引擎新增 `lastElevationStepHpa`——只回报「窗口最后一步」被归为高度事件的量；
- 采集器把这些步进累加成 `elevationOffsetHpa`，并**跨会话持久化**
  （否则重启处会跳一次，同样造出假的「大变化日」）；
- 会话 CSV 落 `weather_pressure_hpa`；小时桶与打卡点都用它；
- `ElevationOffsetAccumulationTest` 直接断言：原始序列下降 7.2 hPa 时，
  解耦后的天气序列跨度 < 1 hPa。

**边界**：修正只对新写入的数据生效。旧 CSV 没有该列，读取时退回原始读数。

### 9.8 速评与正式双层窗口

「3 小时窗口 + 覆盖率 30%」意味着冷启动后要约 54 分钟才有结论，这是矫枉过正。
现在两层：速评（5 分钟窗口）先给结论，正式（3 小时）成熟后覆盖它。

速评的绝对量门限按比例缩到 **0.15 hPa**——沿用 0.5 hPa 会导致 5 分钟内
永远达不到而恒判「平稳」，那就等于没加速评。5 分钟窗口会误判，
这是**已知且明确接受的取舍**：误判的代价远小于干等。

### 9.9 体感佐证：只让有物理因果的信号参与判定

查文献之后，三个信号里只有一条站得住：

| 信号 | 参与判定 | 依据 |
|---|---|---|
| 光照骤降 | **能**（最多升一档） | 云层增厚显著削弱日光，资料把「白天光照突然跌破阈值」当作云量增加的迹象。物理因果：云厚 → 光弱 → 降水近。腕上光传感器受衣袖主导，故只用**相对跌幅**：10 分钟跌 ≥ 40% 且基准 ≥ 200 lux |
| 静息心率 | 不能（只提示） | 「低压导致心率上升」的证据来自**高海拔**（数百 hPa 量级），天气级的几 hPa 差上百倍；气象敏感研究集中于头痛/偏头痛，机理仍是假说 |
| 腕温 | 不能（只提示） | 文献原话：环境温度是腕温最大的混淆项，衣袖内外可差好几度；厂商一律与自身滚动基线比。它反映佩戴与环境，不是天气 |

升档规则刻意保守：**只在气压本身已在下降倾向时最多升一档**，
且「未知」不可被佐证升成已知——否则一次关灯或走进楼道就能报出降雨。

### 9.10 判据来源（阈值要能被追溯）

| 阈值 | 来源 |
|---|---|
| 3 小时降 4 hPa 即风暴前兆 | 气象学「暴风定律」（Secret Law of Storms） |
| 气压变化超过 3.5 hPa 时天气变化可期 | 维基百科「天气预报」气压段 |
| 以变压率做预报，24–48 h 约 70% 准确 | 商用气象站（Ambient Weather）说明 |
| 白天光照突降可视为云量增加 | 环境照度与云量关系的研究 |

## 十一、接下来：数据收集与可靠性验证

代码已经够用了，**剩下的问题是"它准不准"——而这个问题只能靠数据回答**。

### 收集期怎么用

1. **一直戴着、让它跑**（前台服务 + indicator 已实测能长期存活）；
2. **天气变了就点一下实况**（下雨 / 起风 / 晴 / 阴）——不必精确到分钟，按 ±3 小时窗口匹配即可；
3. **有体感就打卡**，能写自定义就写自定义（"起床后右侧发紧"比"头痛"有用得多）；
4. 想起来就点一次「生成 AI 报告」，让它对全局与近期各说一段。

### ⚠️ 会有长空白，而且**不可避免**——这不是 bug

主人 2026-09-11 告知：**手表检测到睡眠时会自动进入睡眠模式（类似轻智能），停掉一切应用**，
否则续航撑不住。而且它**不会自己回来**——用户确认过。

在 Android 里，"停掉一切应用"等价于 `force-stop`：系统把包标记为 stopped，
**`START_STICKY` 与任何广播都拉不回来**，只能由用户手动点开一次。这是平台设计，改不了。

**因此收集期的实际操作是：醒来后点开一次「观风」。** 就这一件事。

已为此做的与**没做**的：

| 措施 | 覆盖范围 |
|---|---|
| 5 分钟 `MAX_GAP_MS` 断档即停 | 3 小时窗口跨越空白后**从零重建**，不会把空洞两端接起来做回归 |
| 锁存快照 6 小时过时即丢（9.6） | 每早的空白约 8 小时 ⇒ 旧过程不会带到第二天。**保守是主人的裁决，理由见 9.6** |
| 小时归档"没数据就不写行" | 空白时段**没有行**，`有效天` 如实少算，不会拿"平稳"去填 |
| 大变化日只按已观测的小时算（**不加"日可评估"门槛**） | 缺夜 ⇒ 当日极差只反映白天+傍晚。**这是主人的裁决**，理由见下 |
| 启动时修补"整点缺失"的过去小时 | 睡着的那一小时曾每夜丢失（见 §6）；现在会从样本文件补回来 |
| `backfillCarriedOver`（§6） | 只补**当前这一小时**内已存在的样本，空白时段不会被伪造 |
| `BootReceiver` | **只覆盖真正的系统重启**。睡眠模式那种 stop 它救不了 |
| ~~任何保活手段~~ | 不存在。不要在这上面再想办法 |

**大变化日为什么不加"日可评估"门槛**（我提过，主人 2026-09-11 否掉）：

> 大变化日不应该改变吧。毕竟白天的时候也很常见 >=3hPa 的。
> 夜里发生了什么我们并不关心。只要标准是一致的，就不会有问题。

这个判断在领域上是对的：**要研究的现象发生在白天**——人白天清醒、有不适才会打卡，
夜里那一段本来就不产生打卡点。缺夜不是"缺测量"，而是**范围本就划在白天**；
加门槛反而会把"白天确实变了 3 hPa、只是夜里没记录"的正常日子判成不可评估。

**残留的一点，读者心里有数即可**：判据是统一的，但每天实际观测到的小时数不统一
（睡得早 6 小时、睡得晚 9 小时）。记录特别短的那几天，"不是大变化日"的证据相对弱。
**不做代码处理**——为它加机制，就把一句"仅供参考"变成了一个会被当成结论的数字。

**怎么读空白**：`guanfeng_samples.csv` 里相邻样本间隔 > 15 秒（3× 采样周期）就是断档；
`hourly.csv` 里整点行的缺失同样是断档。**看到空白先按"睡眠模式"解释，再去怀疑代码。**

### 怎么判断"准不准"（这是本阶段唯一要回答的问题）

把所有阈值都当成**待验证的假设**，而不是结论。每个阈值都有文献出处（见 9.9），
但**出处可靠不等于在我们这儿准确**：

| 要验证的假设 | 判据 |
|---|---|
| 「3 小时降 4 hPa 即风暴前兆」（暴风定律） | 报「高」的那些时段里，实际下雨/起风的占比；以及下了雨的那些时段，我们之前报的是几 |
| 速评窗口的 0.15 hPa/5 分钟门限（拍的值，非推导） | 速评报出的「转差」里有多少是误报（对照实况记录） |
| 高度解耦在高频爬楼/电梯场景下是否仍零误判 | `guanfeng_samples.csv` 里 `elevation_events` 与 `grade` 的关系 |
| 体感佐证（光照骤降）是否真的与转雨相关 | 它触发过的次数 vs 随后 3 小时内的实况 |
| 耗电是否可接受 | `power.csv` 的电量斜率 + `adb shell dumpsys batterystats --charged com.yisiyun.guanfeng` |

**如果发现大量误报，先怀疑阈值而不是算法**：解耦与置信闸门已被真机数据验证过，
未经校准的是那几条**判据阈值**。

### 仍未验证（按重要性）

1. **所有判据阈值都没有经过本地数据校准**——这是当前最大的空白，也是第十一节的整个主题。
   3 小时降 4 hPa、速评的 0.15 hPa/5 分钟、**光照骤降 40%** 的门限，都只有文献出处或工程判断，
   没有一条被"本地实际天气"验证过。
2. **体感佐证尚未在真实降雨中触发过**：逻辑有单测覆盖，
   但没有一次「光照骤降 + 气压下降」同时出现的真机样本。
3. **速评窗口的误判率未量化**：0.15 hPa/5 分钟约为真机平地噪声底的两三倍（判断而非推导）。
4. **AI 报告**：长文本与浮层的实际观感已在真机走过（2026-09-12 主人截图确认）。
   **仍未走过**：命中限流的退避提示、失败重试这两条路径。
5. **耗电**：`dumpsys batterystats` 已经取过了——结论是**这台表上它不可用**
   （连续观测 15 分钟，`20.8 / cpu=11.4 / sensor=9.42` 三个数字一个都没动，
   说明该机型的 `power_profile` 对我们用的传感器给不出分辨率）。
   唯一可信的长放电段是 **18:27→22:39 = 4.20 h / 17% = 4.05 %/h**，
   但那是**心率常开时代的旧构建**。脉冲化之后的 A/B **还没做**：
   表一直放在充电底座上，而充电中的电量读数对耗电分析没有意义。
   要测只能靠正常佩戴一段后、回座再算。
6. **长期后台存活上限**：实测退后台 + 熄屏 70 秒零断档。
   **但睡眠模式会把应用整个停掉且不会自动回来**（主人确认，见第十一节），
   所以"整天连续存活"这件事**不存在**，不要再把它当成待验证项。
   另注：**未插充电底座时的电池状态与插底座时的表现不同**，
   不要用插底座的测试推断电池状态下的保活。
6b. **睡眠模式空白的实际形态还没见过**：还没经历过一个完整夜晚，
   不知道一次睡眠模式会断几小时、恢复后 3 小时窗口要多久才重新可信。
6c. **`BootReceiver` 能不能真收到广播**：ColorOS 可能默认禁止第三方自启，
   要等一次真正的系统重启才知道。**不要因为它的存在就宣称"重启也不怕"。**
6d. **「气压 × 体感」标题的排版**：副标题已改为吃剩余宽度，标题在结构上挤不掉，
   但实际会不会把副标题截断，只有看屏幕才知道——上表那批验证里唯独这一项我看不到。
7. **静息基线仍是单值、且是会话级**：文献里厂商都用多天滚动基线，我们目前重启即从头攒。
   归档里已经存了每天的静息心率，改成 7 天滚动中位数成本很低，但还没做。
8. **报告浮层没盖住底部翻页符**（浮层画在页面内，翻页符在外层壳上）。已知、未修。

### 探测阶段的遗留（与核心功能无关）

- **ECG / 血氧 / PPG 的"测量会话"触发方式**：`registerListener` 返回 true 但零回调，
  疑需特定测量流程（可能涉及 OPPO 私有 SDK 或隐藏 API）。
- **PPG_RAW 16 通道的解析与标定**：原始 ADC 可读，但通道语义与标定属深水区。
- **语音识别引擎是否可离线调用**：Mic 硬件可原生调用已证，识别引擎未验证。
- **光学测量边界为强推断**：由 PPG_RAW 通道命名（仅 G / R / IR）推断硬件无紫外激发源，
  未拆机、无芯片手册佐证。
